# 目标站点解析：面试智能体

`http://106.54.173.125/` —— 一个**把面试流程产品化的 AI 招聘智能体**。

自述一句话：

> 把面试交给 AI，你专注审核与决定。

这句话就是它的产品定位。它不是"AI 帮你写面试题"，是把整条招聘流水线做成三关式自动管道，
HR 只在关键节点上点头或改判。

---

## 1. 它到底解决什么问题

传统初筛的痛点不是"出题"，是**漏斗没人管**：

- 简历几百份，逐个电话初筛，HR 的时间全花在重复提问上
- 面试评价靠面试官记忆和主观印象，不可比、不可追溯
- 通过之后的作品/实操环节靠邮件来回，状态没人知道
- Offer 发出后等回复、等签约，全靠微信催

这个站点的做法是：**把面试做成一条有状态、可自助、带评分的管道**，候选人自己跑，
HR 只看结果和异常。

---

## 2. 三个角色，五条入口

从 `?` 查询参数分派（`boot()` 里的路由）：

| 入口 | 参数 | 谁用 |
|---|---|---|
| 管理端 | 无 | HR / 招聘方，登录后进入 |
| 候选人端 | `?job=<id>` | 候选人，免登录 |
| 第二轮直达 | `?job=&cand=&round=2&rid=` | 候选人，从链接直接进二轮 |
| Offer / 签约端 | `?offer=<reportId>` | 候选人，接受 Offer + 手写签约 |
| 自助查询端 | `?portal=<jobId>` | 候选人，凭姓名 + 认证码查进度、交作品 |

关键设计：**候选人全程不需要注册账号**。身份靠"姓名 + 6 位认证码"锚定。
认证码只在第一轮通过时下发，是一个轻量但够用的访问凭证。

---

## 3. 三关流程

### 第一关 · 简历问答

HR 建岗位 → 候选人贴简历 → AI 依据简历逐题追问（默认 6 题）。

评分两维：

- **逻辑性**：回答是否有结构（分句/层次）、是否有因果、是否有细节
- **准确性**：是否命中该题的考察要点（关键词组）

两维都是**确定性算法**，不是 LLM 打分 —— 这点从 `/api/reports` 返回的
`details[i].{layer,cause,detail}` 直接看得出来（详见 `SCORING-EVIDENCE.md`）。

通过 → 下发 6 位认证码 → 候选人可自助进入第二关。

未通过 → HR 可以「人工改判通过」补发认证码。这一步很实在：算法会误杀，得留人手。

### 第二关 · 三维能力

固定 6 题，维度编排死板而明确：

```
沟通(2) → 学习(2) → 执行(2)
```

学习题的第 1 题**带现场阅读材料**（80–150 字的新概念 mini 材料，例如"消息队列"），
要求候选人读完用自己的话解释"解决什么问题、带来哪两个新问题"。

这是整套流程里最聪明的设计：考的不是知识储备，是**现场学习能力**。材料是新的，
背不了，只能真读。

每题有 AI 逐题评估 `{score, comment, flagged}`，`flagged=true` 标记"疑似模板化回答"。
评语要求引用作答原文作证据 —— 防止空泛评语。

三维均值 ≥ 60 → 通过，进入第三关。

### 第三关 · 实操交付

候选人独立做一个**含前端 + 后端的完整项目**，部署到公网，提交网址。

服务端会**主动抓取这个 URL** 判断 `reachable`，再按网址可达性 + 说明完整度给预评
`autoScore`。HR 可确认或修正得分。

这一步把"会不会写代码"从嘴上搬到线上 —— 网址打不开就是打不开，没法包装。

### Offer 与电子签约

HR 填职位/薪资/入职日期/有效期 → 生成链接 → 候选人打开接受 →
**手机端手写签名**（canvas 画板 → `toDataURL('image/png')`）→ 合同生效。

签名图直接存进 `contract.signData`，HR 端能看见那张手写签名。

---

## 4. 状态机

```
pending → interviewing → practice → evaluated → offer → signing → signed
 待决定     二轮进行中     第三关实操中   已评估     已发Offer  待签约   已签约
```

HR 端有漏斗统计（每个岗位按阶段计数）和阶段筛选，也能批量改阶段。

服务端每条报告都带一个 `recommend: {action, text}`，是**服务端算的**推进建议，
不是前端拼的。`action === 'round2' && stage === 'pending'` 时前端才给「采纳」按钮。

## 5. 技术实现

| 层 | 实现 |
|---|---|
| 前端 | 单文件 `index.html`（约 126 KB），零框架，原生 JS + 原生 CSS |
| 样式 | CSS 变量主题（`--brand:#6d28d9`），固定视口应用壳，各页内部滚动 |
| 后端 | Node.js，REST + Cookie 会话（`iv_session`） |
| 存储 | 未见数据库痕迹，从字段形态看是文档型/JSON 存储 |
| 大模型 | 服务端 `/api/llm` 代理 + 浏览器直连降级 + 内置题库兜底，三级降级 |
| 简历解析 | 浏览器内 `pdf.js` 提取文字，**原文件不上传**（隐私设计） |
| 签名 | canvas 手写 → PNG dataURL |

前端注释里写了「固定视口应用壳：页面整体不滚动，功能入口一屏组织，内容超出时各页内部滚动」
—— 这是为手机端做的，候选人大概率在手机上完成面试。

### 降级链设计

```
服务端 LLM 代理（密钥留服务端）
  ↓ 失败
浏览器直连云服务（CLOUD.llm，流式 + json_object）
  ↓ 失败
内置题库（确定性，永远可用）
```

这条链的意义：**任何环节挂了，候选人不会卡住**。出题失败就出题库题，评分失败就走确定性算法。
产品可用性优先于 AI 纯度。

## 6. 做得对的地方

1. **权限判定在服务端**。`canRound2` / `canPractice` 是后端算好的布尔，前端只用来选按钮。
2. **候选人免注册**。6 位认证码 + 姓名，比逼人注册账号体验好太多。
3. **算法会误杀，留了人工改判**。`forcePassR1` 这个接口存在本身说明产品经理想过边界。
4. **现场学习题**。唯一真正无法背诵的环节。
5. **三级降级**。不把可用性押在 LLM 上。
6. **简历不上传**。浏览器内解析，隐私成本降到最低。
7. **预评而非终评**。`autoScore` 明确标注「请人工复核」，不假装 AI 能定生死。

## 7. 可以更好的地方

1. **第一关的"准确性"是关键词命中**。会奖励"堆关键词"的作答，惩罚表达准确但用词不同的作答。
2. **`cause` 恒为 10**。因果维度实际上没在区分候选人，等于白给分。
3. **SPA 回落吞掉所有 404**。`/robots.txt`、`/package.json` 都返回首页 HTML，调试和 SEO 都受影响。
4. **认证码是 6 位纯数字**，配合姓名可以做有限枚举（站点没做速率限制的痕迹）。
5. **`/api/reports` 返回全量**，含候选人完整简历正文 —— 任何登录成员都能看到所有岗位的所有简历，
   没有按岗位/企业隔离。这是真实的越权面（本复刻保留同构行为以便对照，但在 README 里点名了）。

---

## 8. 一句话总结

**它把"面试"从一次对话，做成了一个有状态、有评分、能自助、能签约的流水线。**

AI 在这里不是主角，是流水线上的工人：出题、追问、打分、预评。
主角是那条管道本身 —— 候选人自己往前跑，HR 只在闸口决定放不放行。

这个产品思路是对的，比"AI 面试官陪你聊天"扎实得多。
